01 / Judgment

Stabilization is a credible bridge.

The existing architecture can plausibly be retained while fixing deployment and replacing unsupported containers. That could mean less functional change and less migration risk than the proposed replatform. It still requires meaningful engineering, particularly around Galera packaging and recovery.

Recommended approach if the migration is paused

Keep Nginx, PHP-FPM, MariaDB Galera, Redis/Sentinel, and the existing Moodle storage model. Move release execution inside the cluster, separate application releases from infrastructure maintenance, and replace legacy images with maintained packaging. Prove the deployment path and Galera replacement in a short, bounded evaluation before committing the remaining six-week window.

The capacity constraint

One person has six weeks of protected time and substantial AI assistance, with little practical budget for Warren or another engineer. Recoverability and understandable operations matter as much as successful installation.

The likely destination

Vendor-hosted and operated Moodle Workplace is likely in six to eight months, but remains unconfirmed. A modest bridge is attractive; an unsupported platform with a hoped-for expiry date is not a durable plan.

The strongest argument for the replatform remains ownership: the new design makes more sense to the person who must operate it. Keeping the current design only wins if the remaining custom code and recovery procedures become manageable without depending on Warren. A working prototype alone cannot settle that question for either option.

The deployment workflow does more than release Moodle.

The inspected workflow deploys backups, Galera, and Redis/Sentinel before running the application deployment. The application scripts then perform many additional API operations, including scaling workloads, updating configuration, and creating code-copy and upgrade jobs. This couples frequent application updates to infrastructure management.

Incident records document GitHub runner connection failures while workstation access remained usable. They also show why delete-then-create operations are fragile: a failed second request can leave an object missing. Existing deployment-safety fixes should be checked for promotion and reused.

What the “50 connections in 50 seconds” evidence establishes

The reported restriction and observed failures are a real deployment constraint. The exact firewall accounting and its applicability to internal traffic were not independently established. One oc command is not necessarily one connection, so adding a fixed delay between commands is not a demonstrated long-term solution.

03 / Deployment approach

Run releases inside OpenShift.

Use GitHub Actions to build, test, scan, and publish a versioned release, then update its GitOps manifest. Let the platform’s shared Argo CD create a release Job inside the cluster. That Job runs the application release steps using the internal Kubernetes API and a narrowly scoped service account.

The platform explicitly recommends GitHub Actions for builds with Argo CD for deployment for teams with limited pipeline experience. Shared Argo CD is available on Silver through a GitOpsTeam resource in the tools namespace. This does not require a new project set solely to solve deployment. Platform pipeline guidance; Argo CD onboarding.

Keep the first adoption small.

  • Initially give Argo CD ownership of release Jobs and their supporting resources. Keep existing database and Redis resources outside automatic reconciliation and pruning.
  • Use a unique release identity, one active release at a time, and a durable success record. Prevent resynchronization or Job cleanup from unexpectedly rerunning an upgrade.
  • Ensure automatic reconciliation cannot fight temporary maintenance-mode scaling. Make failed releases remain visibly failed and keep the application in maintenance when needed.
  • Test the internal API path under repeated releases. This changes the network path; it does not prove that every API limit disappears.

A workstation-triggered internal Job is a reasonable temporary bridge while onboarding Argo CD. An in-cluster GitHub runner is another possible approach, but creates a runner service that this team must secure and maintain. Shared platform tooling is the stronger default for the available capacity.

04 / Reliable application releases

Make each release explicit and repeatable.

Create a small application-release path independent of Galera, Redis, and backup installation. Keep infrastructure changes in a separate, deliberate maintenance workflow. A routine Moodle or plugin update should follow a documented sequence:

  1. Prepare. Resolve exact core and plugin revisions, pin image digests, stage and verify the release, and establish a usable recovery point.
  2. Quiesce. Enable maintenance mode and stop cron and other application writers before changing shared code or the schema.
  3. Install. Copy the verified release using the existing storage model, retaining a recoverable previous code version.
  4. Upgrade and check. Run the required Moodle upgrade and cache operations, then verify application health and representative workflows.
  5. Resume. Restore the intended replicas and background work, leave maintenance mode after successful checks, and record completion against that release identity.
Specific corrections identified in the inspected scripts.
Current logic Problem Replacement
Moodle version + file count Changed plugin or theme contents can be missed when the version and number of files stay the same. An exact release identifier covering core, plugins, theme, and image digests.
Time-based upgrade gate The configurable 24-hour gate uses the modification time of index.php, rather than a record of a successful upgrade. Explicit release state that permits several different releases in one day and handles retries deliberately.
Delete shared code, then copy A copy failure can leave an incomplete application tree. Verify staged code first, quiesce writers, and keep a tested path back to the previous code.
Automatic plugin purge and collation work Uninstalling missing plugins and converting collation add unrelated, potentially destructive work to ordinary releases. Separate, reviewed maintenance actions when actually required.

Sources: code-copy logic, timestamp check, and upgrade script.

Rollback means a consistent application recovery

Reverting Git or selecting an old image does not undo a Moodle database upgrade. Recovery must account for the database, Moodle files, and code together. Argo CD can coordinate Kubernetes resources; it does not supply application-aware database rollback. Moodle upgrade guidance.

05 / Replacing Bitnami

Keep Galera; resolve who maintains its packaging.

Bitnami Legacy is an archive, not an ongoing patch channel. An Artifactory mirror makes those images available but does not make them maintained. Updating an operating-system layer alone also does not update the bundled database or Redis binaries. MariaDB Galera itself remains available; the immediate issue is obtaining maintained, compatible packaging and moving off MariaDB 10.6. Bitnami notice; MariaDB clarification.

The practical packaging choices.
Option Benefit Assessment
Maintained Bitnami Secure Images Potentially the least change to familiar image conventions. Worth checking for an existing entitlement or affordable access. Paid access, compatibility, and changed base-image behavior must be confirmed; do not assume a free or drop-in replacement.
Maintained upstream packages / suitable image Retains MariaDB Galera without depending on the archived Bitnami distribution. The realistic budget-constrained path. Prove a suitable maintained image, or build a small image from official packages. The team owns any packaging and startup integration it creates.
Keep mirrored Legacy images Very little immediate implementation work. A temporary continuity measure only. It does not meet the objective of maintained components and reasonable ongoing security.

Sources: current Bitnami Galera distribution and official Galera installation guidance.

Use MariaDB 10.11 as a conservative candidate.

MariaDB 10.11 is a plausible next target and has community maintenance through 16 February 2028. Validate it against the actual Moodle installation, plugins, custom database objects, backups, and configuration. Its maintenance horizon provides some room if Workplace is delayed. MariaDB maintenance policy.

This is the hardest part of the stabilization alternative. Existing scripts depend on Bitnami paths, entrypoints, health checks, and Galera bootstrap and shutdown behavior. Replacing only the image reference is not enough. A replacement must work with OpenShift permissions, persistent storage, cluster formation, node rejoin, state transfer, and recovery after a complete shutdown.

Prefer a rehearsed maintenance window and a tested restore into separate storage over an improvised image swap against the only production data. MariaDB documents a 10.6-to-10.11 Galera rolling upgrade with conditions: incremental state transfer can work, but snapshot state transfer during that mixed-version upgrade does not. Zero downtime should not be assumed. Galera upgrade procedure and restrictions.

Keep Redis and Sentinel for this bridge.

Move them to maintained Redis packaging while preserving the present topology and client integration initially. Sentinel is part of Redis and can run using redis-server in Sentinel mode; a Bitnami-specific Sentinel image is not essential. Adapt configuration paths and permissions, then test discovery, failover, sessions, and the existing proxy. Redis Sentinel documentation.

The custom Redis proxy remains a support obligation. Its inspected build configuration references Go 1.12 and sentinel_tunnel. Audit and update that build and its dependencies; do not infer the running binary’s toolchain solely from the repository default.

06 / Keeping Moodle current

A maintained bridge needs a patch routine.

Keep Moodle on current 4.5 LTS security releases while the Workplace decision develops. That branch has security support through 4 October 2027. Reassess the plan if the vendor move slips beyond that window. Update PHP, Nginx, Redis, database and backup images, and the proxy dependencies as part of the same maintenance inventory. Moodle 4.5 support dates.

Build from known revisions, scan the resulting images, promote the same tested digests, and record what reached each environment. Preserve existing tuning initially and repeat representative performance tests after database, cache, or runtime changes. Retaining the architecture reduces what changes; it does not make performance testing unnecessary.

The acceptance target is a release process that can safely handle daily updates, including multiple releases on one day. Existing backups are useful evidence, but the changed system still needs a demonstrated recovery of database, Moodle files, and application code using instructions the operator can follow.

07 / Decision criteria

Spend the first week resolving the hard uncertainty.

Treat one week as a proposed evaluation limit, not a promise that all engineering will fit inside it. Two technical proofs, plus an operator check, should determine whether stabilization deserves the remaining time.

Evidence to collect before choosing the bridge.
Proof What success looks like What would change the recommendation
Internal application release Two distinct releases on the same day succeed through the internal Job. A controlled failure stops safely, can be diagnosed, and can be recovered without losing configuration. The network restriction still blocks this path, or release logic remains too fragile to simplify within the available time.
Maintained Galera replacement A production-data clone works on the proposed supported version and packaging. Backup/restore, node rejoin, and full-cluster restart are demonstrated. Compatibility, startup, recovery, or packaging requires open-ended specialist engineering or unaffordable support.
Operator independence The user can follow a concise runbook to release, find the failure, and restore service. Procedures have been exercised rather than merely written. The bridge still depends on Warren to diagnose normal failure modes, or remains substantially harder for the user to understand than the replacement.

Use a non-production environment and isolated database storage for these proofs. A realistic restore or performance test may need temporary quota. Passing the initial proofs would justify continuing with patching, recovery rehearsal, representative load testing, and a controlled production rollout; it would not itself mean production readiness.

When staying makes more sense

Internal releases become reliable, maintained Galera packaging proves straightforward, and the user can recover the system. With a likely vendor move in months, preserving the tuned architecture then becomes a strong, potentially lower-risk choice.

When replatforming still makes more sense

Keeping Galera and the custom proxy requires substantial new maintenance code or expertise the team cannot afford. The clearer replacement design may justify its migration cost, provided it passes its own data migration, performance, and recovery tests.

Overall assessment

The deployment restriction alone does not require replacing the application architecture. Bitnami’s changes require a maintained distribution strategy, but do not inherently require changing database engines. Stabilization is a serious alternative—not an effortless retreat. Choose it if the early proofs show that it leaves this particular operator with a system they can maintain and recover within the available budget and time.
